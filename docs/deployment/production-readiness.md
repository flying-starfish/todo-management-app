# 本番化チェックリスト

このドキュメントは「公開前に確認する項目」を列挙するだけでなく、なぜその確認が必要かを理解するための学習資料です。

## 学習目的

- 開発環境と本番環境で重視点が変わる理由を理解する
- 機能完成と運用可能性の違いを説明できるようになる
- リリース判断を感覚ではなく観点ベースで行えるようにする

## 本番化の基本思想

### 1. 動くことより、壊れ方が予測できること

本番では「失敗しない」より「失敗時に被害を限定し、復旧できる」ことが重要です。

### 2. 設定はコードと同じくらい重要

環境変数、接続情報、CORS、ログ設定の不備は、コード不具合と同等の障害要因になります。

### 3. セキュリティは追加機能ではなく前提条件

認証・認可・秘密情報管理・依存関係監査は、実装後に足すのではなく継続的に維持します。

## セキュリティ

- 強力な `SECRET_KEY` を設定
- `ENVIRONMENT=production` を使用
- CORS 設定を本番ドメインに限定
- HTTPS 終端とセキュリティヘッダーを確認

### なぜ必要か

- `SECRET_KEY` の弱さはトークン偽造リスクに直結する
- 開発向け設定のまま公開すると、情報漏えいや不正アクセスの入口になる

## データベース

- PostgreSQL 接続文字列を確認
- マイグレーション手順を確認
- バックアップ手順を用意

### なぜ必要か

- 接続文字列の誤りは起動不可や誤接続の原因になる
- マイグレーションの手順不備は、データ不整合やダウンタイムを生む
- バックアップがない状態は、障害時にサービス継続不能となる

## アプリ設定

- ログレベルを `INFO` 以上に設定
- `.env.production` を整理
- ヘルスチェックエンドポイントを確認

### なぜ必要か

- `DEBUG` ログは機密情報露出や性能低下につながる
- 設定漏れは「特定環境だけ失敗する」典型要因
- ヘルスチェックは監視と自動復旧の基盤になる

## CI/CD

- テスト・Lint・型チェック・脆弱性スキャンが通る
- Docker イメージがビルド可能
- デプロイ先の環境変数が定義済み

### なぜ必要か

- 品質ゲートを通過していない変更は本番での不具合確率が高い
- イメージ再現性がないとロールバックや横展開が難しくなる

## リリース前の最終確認

- 新規登録・ログイン・Todo CRUD の動作確認
- フロントから API への接続確認
- 監視ログの確認

## リリース判定の実践観点

### Go / No-Go の最低基準

- 認証つき主要機能が通る
- 重大なセキュリティ警告が残っていない
- 障害時の一次対応手順がある

### 見落としやすいポイント

- 環境変数はあるが値が空
- CORS がワイルドカードのまま
- WebSocket やバックグラウンド処理の監視が未整備
