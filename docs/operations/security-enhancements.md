# セキュリティ対応メモ

このドキュメントは、セキュリティ改善の要点だけを記録します。

## 学習目的

- 実装した対策を「なぜ必要か」まで含めて理解する
- 攻撃シナリオを想定し、予防策と検知策を分けて考える
- 改善履歴を残し、再発防止に活かす

## セキュリティ方針

### 1. 認証されていない操作を最小化する

公開 API や WebSocket は、利用者を特定できない状態での情報露出を避けます。

### 2. 1層だけで守らない

認証、入力検証、ヘッダー設定、依存関係監査を組み合わせ、単一対策の抜け漏れを補います。

### 3. 失敗を前提に観測可能にする

ログと監視を整え、異常時に「何が起きたか」を追跡できる状態を重視します。

## 実施済み

- 認証: JWT ベースの認証
- パスワード: ハッシュ化保存
- 脆弱性スキャン: `pip-audit` / `npm audit`
- CI 連携: セキュリティチェックを自動実行
- フロントエンド: Vite 構成へ移行済み

## 直近の重要対応（WebSocket 認証強化）

### 背景

以前は WebSocket エンドポイントが未認証でも接続可能で、Todo 更新イベントが全接続へ配信される余地がありました。

### 対応内容

- WebSocket 接続時にトークン必須化
- 検証失敗時は接続拒否
- Todo イベントをユーザー単位配信へ変更
- 送信失敗した接続のクリーンアップを追加

### 学習ポイント

- 「アプリ画面がログイン必須」だけでは不十分
- API/WS の入口ごとに認証制御を明示する必要がある
- リアルタイム配信は受信対象の設計が最重要

## 想定脅威と対策の対応表

- 不正ログイン試行: レート制限の導入を継続タスク化
- トークン偽造・漏えい: 強力な SECRET_KEY と短い有効期限を運用
- 依存関係の既知脆弱性: CI で継続監査
- 誤設定による情報露出: 本番チェックリストで事前検証

## 継続タスク

- レート制限の導入
- セキュリティイベント監視の強化
- 本番ドメイン向け CORS / ヘッダーの定期見直し
