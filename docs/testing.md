# テストガイド

このドキュメントは、実行コマンドだけでなく「何を、なぜテストするか」を学ぶためのガイドです。

## 学習目的

- バックエンドとフロントエンドで、テストの責務をどう分けるか理解する
- リファクタや機能追加で壊れにくいコードを作る考え方を身につける
- CI で自動化される品質ゲートの意味を理解する

## このプロジェクトのテスト思想

### 1. API 契約を守る

バックエンドでは「レスポンス形式・ステータスコード・認証要件」を契約とみなし、仕様の後退を防ぎます。

### 2. UI の見た目より振る舞いを検証する

フロントエンドでは、実装詳細ではなくユーザー操作に対する結果を中心に確認します。

### 3. テストは速く、失敗理由が明確であること

失敗時に原因が追いやすいテストを優先し、過度に重い E2E 的テストを増やしすぎない方針です。

## テスト戦略（簡易ピラミッド）

- 多め: 単体テスト（ロジック・バリデーション）
- 中間: API/コンポーネント統合テスト
- 少なめ: 重い結合テスト

このバランスにより、開発速度と品質の両立を狙います。

## バックエンド（pytest）

```bash
cd backend

# 通常実行
pytest

# カバレッジ付き
pytest --cov=app

# 推奨（整形・Lint・セキュリティ・テスト）
make check-all
```

### バックエンドで重視する観点

- 認証が必要なエンドポイントのアクセス制御
- Todo CRUD の正常系と異常系
- スキーマ変更時の後方互換（型・必須項目）

詳細は [backend/PYTEST_GUIDE.md](../backend/PYTEST_GUIDE.md) を参照してください。

## フロントエンド（Vitest）

```bash
cd frontend

# ウォッチ実行
npm test

# 1回実行
npm test -- --run

# カバレッジ付き
npm run test:coverage

# 推奨（整形・Lint・型チェック・テスト・セキュリティ）
make check-all
```

### フロントエンドで重視する観点

- ログイン状態の遷移
- API エラー時の表示と復旧導線
- 優先度や完了状態など、Todo 操作の反映

## CI で確認している主な観点

- バックエンドのテスト
- フロントエンドのテスト
- Lint / フォーマット
- 型チェック
- 脆弱性スキャン

## よくある失敗と対処

### 1. テストが実装詳細に依存しすぎる

失敗例:
- コンポーネント内部の state 名や関数呼び出し回数に依存する

対策:
- 画面出力や API 入出力の契約を軸に検証する

### 2. 1つのテストで複数責務を検証する

失敗例:
- 認証、作成、並び替え、削除を1本にまとめる

対策:
- 失敗時の原因切り分けを優先し、小さなテストに分割する
